### Current defaults

Publisher max-age is a freshness bound on **superseded groups**. A group expires when either its successor's arrival is old enough at this hop or the successor's first timestamp trails the live edge enough. Untimed tracks use the wall clock. The newest group is exempt. Byte reclamation has a separate cache policy. See [rs/moq-net/src/model/track.rs:120](https://github.com/moq-dev/moq/blob/c95a9b1201/rs/moq-net/src/model/track.rs#L120) and [js/net/src/track.ts:137](https://github.com/moq-dev/moq/blob/c95a9b1201/js/net/src/track.ts#L137).

Cache capacity is a converging target, not a hard memory limit. Live edges remain protected; active reads can keep Rust idle-LRU entries fresh (JS uses write activity); an unbounded byte target plus a time window does not bound bytes, group count, publisher count, or an arbitrarily large newest group. ### Subscriber and wire absence are separate

- Rust subscriptions default to `max_delay = Some(0)`; JS omitted subscriber `maxDelay` means 0. Explicit Rust `None` / JS `null` uses publisher retention alone. Changing publisher retention is not another latency-default change. See [rs/moq-net/src/model/subscription.rs:23](https://github.com/moq-dev/moq/blob/c95a9b1201/rs/moq-net/src/model/subscription.rs#L23) and [js/net/src/track.ts:233](https://github.com/moq-dev/moq/blob/c95a9b1201/js/net/src/track.ts#L233).
- A direct fetch has its own options, defaulting to no *subscriber* cap. It still obeys publisher/local retention: Rust `Fetching::poll` clamps the budget and returns `Error::Old` before serving stale data. A more tolerant subscriber cannot recover history expired by publisher policy. See [rs/moq-net/src/model/group.rs:4112](https://github.com/moq-dev/moq/blob/c95a9b1201/rs/moq-net/src/model/group.rs#L4112) and [rs/moq-net/src/model/track.rs:5531](https://github.com/moq-dev/moq/blob/c95a9b1201/rs/moq-net/src/model/track.rs#L5531).
- For an IETF SUBSCRIBE with absent MAX_AGE, Rust's `serving_subscription` sets `max_delay = None`; JS uses its largest safe integer budget. This means no additional subscriber restriction, **not guaranteed unlimited storage**. Explicit MAX_AGE overrides this. See [rs/moq-net/src/ietf/publisher.rs:30](https://github.com/moq-dev/moq/blob/c95a9b1201/rs/moq-net/src/ietf/publisher.rs#L30), [rs/moq-net/src/ietf/publisher.rs:1932](https://github.com/moq-dev/moq/blob/c95a9b1201/rs/moq-net/src/ietf/publisher.rs#L1932), and [js/net/src/ietf/publisher.ts:504](https://github.com/moq-dev/moq/blob/c95a9b1201/js/net/src/ietf/publisher.ts#L504).
- The checkout's Timestamp extension says SUBSCRIBE absence preserves publisher delivery policy and update absence preserves the current budget; zero expires superseded groups, never the newest. This is extension semantics, not a base-IETF default of zero: [drafts/draft-lcurley-moq-timestamp.md:142](https://github.com/moq-dev/moq/blob/c95a9b1201/drafts/draft-lcurley-moq-timestamp.md#L142). The published [timestamp-01](https://www.ietf.org/archive/id/draft-lcurley-moq-timestamp-01.html) predates this MAX_AGE section; do not cite that revision as specifying it.
- Base [moq-transport-22 section 10.3](https://www.ietf.org/archive/id/draft-ietf-moq-transport-22.html#section-10.3) defines a different property, MAX_CACHE_DURATION: absence allows caching until implementation constraints evict objects. Its present-value rule measures age from receipt of each object, unlike this model's superseded-group freshness. The implementation maps publisher age to that property ([rs/moq-net/src/ietf/properties.rs:89](https://github.com/moq-dev/moq/blob/c95a9b1201/rs/moq-net/src/ietf/properties.rs#L89)). That pre-existing distinction is not resolved by choosing an authored default. No wire omission is reinterpreted in this proposal.

### Concrete consequences

For a live feed with successive groups A then B, **zero publisher age makes A stale as soon as B supersedes it**, even if A's payload remains allocated until cache reclamation. A late join can still read the newest retained B from its start, including its keyframe or snapshot. Zero does not inherently break every late join. It removes overlap for catch-up, switching/warmup that needs A, and direct fetching of A once superseded. Even with zero, the newest group can be large or old in absolute time.

With **30 s publisher age**, a reader can request superseded groups within the age window, provided they remain cached or can be filled. That does not delay a default live reader, whose own budget is still zero. The window is measured at group reach, not an exact 30 s of first-frame history, and idle expiry, byte pressure, upstream availability, track lifetime, and decoder needs can shorten useful history. This is eligibility, not a guaranteed DVR service level.

HLS/DASH needs past media for listed segments and players starting several target durations behind live. Zero media retention makes those segment fetches fail once their media groups are superseded. A finite value must cover the advertised playlist and fetch/reorder needs; 30 s is the existing media policy, not a proof that every possible playlist configuration fits. The HLS record track is different: its newest group restates its window.

DVR and archive need two policies: enough live overlap to record reordered groups without gaps, and durable storage retention to seek later. Zero source age can lose superseded content before recording or eliminate reorder tolerance; it does not erase bytes already stored. Thirty seconds is not a long DVR. Archive replay deliberately advertises no publisher limit, so historical reads remain possible while the store retains them; a relay's local ceiling may still restrict them. Keep this intentional exception explicit.

### Proposal for the maintainer

**Recommendation: use 30 s for newly authored raw tracks as well as media, with explicit unlimited available; preserve received absence and archive playback semantics.** This reuses the existing Rust/JS media window and leaves more than the recorder's default 10 s reorder allowance under normal cache availability. It avoids zero's loss of overlapping groups without making live viewers wait. It is a product default, not a measured optimal duration or a memory safety claim. Do not change relay transit ceilings, byte budgets, cache expiry, wire codecs, or absence semantics as part of that choice.

Choose one authored policy:

1. **30 s raw and media (recommended).** Omitted authoring configuration becomes finite across Rust, JS, and bindings. Snapshot/catalog producers may explicitly choose zero because their latest group bootstraps a join; retain explicit longer application policies where needed. This bounds accidental readable history but changes consumers that relied on unlimited raw history.
2. **0 raw, keep 30 s media.** Cheapest ordinary historical delivery for raw snapshots/live data, but append logs, catch-up, warmup, and past-fetch users must opt in. Zero still does not imply immediate payload reclamation. This requires a broader consumer audit before implementation.
3. **Keep raw unlimited; finite media only (today).** No migration, but accidentally unbounded publisher freshness remains. The 30 s idle cache does not replace an authored age policy.

The scope choice is also the maintainer's: preserve relay `duration` unset as no ceiling (**recommended**), or default it to 30 s too. A finite relay ceiling limits long-DVR/archive delivery regardless of an explicit unlimited publisher; it needs a clear operator opt-out and a deliberate product decision. It cannot be smuggled in as parity with the existing 30 s idle LRU.

### Migration and implementation boundaries, if approved

- Separate an omitted *authoring* option from explicit unlimited and from absent *received metadata*. Rust `None` and FFI null already mean unlimited; preserve that meaning. Rust authored defaults would become `Some(30 s)`, while conversions must preserve explicit `None` instead of conditionally inheriting a changed default. C's absent presence flag needs the same deliberate treatment.
- JS currently conflates omitted authoring fields with absent decoded metadata in `infoDefaults`, and has no publisher-null unlimited value. A possible authoring shape is omitted/undefined = 30 s, `null` = unlimited, finite milliseconds = that policy; decoded `Info` must still preserve wire absence. This public API shape needs maintainer approval. Prefer applying defaults at producer construction, with nullable authoring options that preserve decoded metadata. An alternative is an explicit default/unlimited/finite retention type across authoring APIs, at the cost of a new surface in every binding. Do not change `infoDefaults` globally and silently give incoming tracks 30 s.
- UniFFI generated constructor defaults and hand-written Python, Swift, Kotlin, Go, Dart, C, and C++ wrappers must consistently distinguish omission and explicit unlimited. In particular, the current UniFFI `if let Some` and C `if max_age_present` conversions would inherit a changed Rust default for explicit unlimited. Fix those conversions in the implementation, rather than advertising an escape hatch that fails.
- Existing media stays at 30 s. Rust mux `with_max_age(None)` and JS hang's omitted helper option currently mean inherit, so an unlimited-media option needs a deliberate API decision, not a new interpretation of those calls without migration. Preserve explicit archive `.with_max_age(None)`, catalog/snapshot usability, and application-specific 5 s/one-day policies unless their consumers justify a change.
- Raw publishers relying on more than 30 s must explicitly request a longer window or unlimited at construction; do this before publishing a new track/broadcast identity. Readers asking for history must also set a sufficient max-delay and ranges. Configure relay ceilings and cache capacity/expiry for the intended service; disabling publisher age alone is insufficient.
- The implementation is a behavioral/API change: identify released affected surfaces, mark a breaking PR title with `!` where applicable, describe migration in its Impact, update Rust/JS/bindings and user docs together, and leave release-owned `MIGRATE.md` sections to the release cut. Wire values/absence remain unchanged; only authored advertisements differ. Any separately chosen wire change needs its matching draft updated.
- Verify authored omission versus explicit unlimited, decoded absence, timed/untimed supersession, a late join to an unchanged latest snapshot, direct old-group fetch, media segment fetch, and archive replay across the chosen window. Use mocked time and existing test harnesses; run selected checks and all-language interop for the implementation's API/FFI/wire scope. Re-check overlapping PRs rather than duplicating their fixes.

Remaining work: the maintainer chooses authored policy, relay-ceiling scope, and the authoring API boundary/unlimited representation; then `/quest-plan` records the implementation. This draft is a research checkpoint, not approval to implement or merge.
